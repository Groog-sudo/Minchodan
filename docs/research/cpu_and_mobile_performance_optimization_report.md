## 1. 개요 및 시스템 환경 제약

본 문서는 GPU 가속 하드웨어가 부재한 순수 CPU 전용 PC 환경(예: Intel i7-8700 CPU)과 모바일 단말(Android/iOS)의 자원 제약 하에서 발생할 수 있는 주요 성능 및 기능적 결함을 조명하고, 하드웨어 증설 없이 소프트웨어 레벨에서 지연 시간을 단축하고 연산 안전성을 확보하기 위한 최적화 계획과 그에 따른 부작용의 해소 방안을 기술합니다.

## 2. 성능 및 기능 관점의 4대 문제점

| 분류 | 문제점 정의 | 주요 원인 및 영향 |
| :--- | :--- | :--- |
| **성능** | **CPU 서버 YOLO 추론 지연 및 FPS 저하** | - PyTorch CPU 기본 연산 속도 한계로 객체 탐지/노면 분할 CPU 추론 시간이 증가.<br>- 동적 FPS 장치 작동으로 프레임 전송 주기가 **250ms에서 450ms**로 늘어나 실시간 회피 가이드 지연 발생. |
| **성능** | **실기기 온디바이스 TFLite 추론 미작동** | - 이미지 디코딩 및 `Float32Array` 생성 연산이 모바일 CPU를 100% 점유하여 OS에 의해 강제 종료되는 현상 방지를 위해 배열 송신을 생략함.<br>- 이로 인해 온디바이스 추론이 동작하지 않고 모든 판단을 서버에만 전적으로 의존하는 구조적 리스크 내포. |
| **기능** | **LLM + TTS 인지 경로 가이드의 누적 지연** | - `프레임 수신` -> `YOLO 탐지` -> `RAG 검색` -> `Gemini API 호출(0.5~1.5초)` -> `WAV 파일 실시간 합성(0.2~0.5초)`에 이르는 전체 흐름의 지연 시간이 누적됨.<br>- 최종 가이드가 출력되는 시점에는 이미 보행자가 장애물에 도달하여 가이드 실효성 상실 우려. |
| **기능** | **ngrok 무료 계정 주소 유동성 및 재빌드 병목** | - ngrok 재기동 시 퍼블릭 외부 주소가 매번 무작위 변경됨.<br>- 변경될 때마다 모바일 소스코드(`WS_URL`)를 수동 수정하고 다시 빌드/배포하거나 Metro 번들러를 재시작해야 하는 개발 병목 발생. |

## 3. CPU 및 소프트웨어 중심 개선 방향

### A. YOLO ONNX Runtime CPU 가속 변환
- **설명**: 기존 PyTorch `.pt` 가중치를 C++ 기반으로 최적화된 ONNX 포맷(`.onnx`)으로 변환하여 CPU 연산 성능을 극대화합니다.
- **기대 효과**: CPU 단독 추론 환경에서도 PyTorch CPU 연산 대비 약 2~3배의 추론 속도 단축이 가능합니다.

### B. 온디바이스 Zero-copy 픽셀 포인터 연동
- **설명**: 모바일 JavaScript 단에서의 부하를 유발하는 이미지 픽셀 가공 연산을 전면 배제하고, 네이티브 단(Java/Objective-C)에서 직접 프레임 버퍼 주소를 TFLite 입력 텐서로 주입합니다.
- **기대 효과**: JS 싱글 스레드의 차단(Block) 현상을 예방하고, 실기기에서 무선 환경 단절 시 백업 역할을 수행할 수 있는 온디바이스 백업 가속기를 온전히 활성화합니다.

### C. LLM 스로틀링 및 TTS 음성 파일 캐싱
- **설명**: 프레임이 수신될 때마다 무조건 RAG 및 LLM을 수행하는 비효율을 방지하기 위해, 탐지 대상의 유의미한 변화가 포착될 때만 선별적으로 오케스트레이션을 가동합니다.
- **기대 효과**: LLM 및 실시간 TTS(pyttsx3) 호출 횟수를 급감시키며, 자주 재생되는 안전 가이드 음성은 WAV 바이너리로 메모리에 캐싱해 둠으로써 즉각적인 반응 속도를 확보합니다.

### D. ngrok 고정 도메인 및 동적 서버 설정 UI 도입
- **설명**: ngrok 무료 플랜에서 계정당 1개 무료 제공되는 정적 도메인(Static Domain)을 발급받아 환경 변수에 영구 지정하고, 모바일 앱 초기 진입 창에 텍스트 주소 입력 모달을 배치합니다.
- **기대 효과**: 터널 재시작에 따른 앱 재패키징/재빌드 오버헤드를 원천적으로 청산합니다.

## 4. 개선 방향 적용 시의 잠재 리스크 및 대처 방안

### [1] YOLO ONNX 가속 변환 리스크

* **잠재 리스크**:
  * 순수 `onnxruntime` 패키지를 단독 활용할 경우 NMS(중복 박스 제거) 및 Segmentation 마스크 디코딩 후처리 로직을 수동으로 파이썬으로 구현해야 하며, 후처리 성능이 낮을 경우 오히려 지연 시간이 늘어날 수 있습니다.
* **대처 방안**:
  * **YOLO Ultralytics ONNX 백엔드 활용**: 후처리 코드를 직접 작성하는 대신, Ultralytics 라이브러리가 제공하는 모델 연동 옵션(`model = YOLO("best.onnx")`)을 통해 가중치만 ONNX로 교체하여 기존 NMS 후처리 엔진을 안전하게 공유합니다.

### [2] 실기기 온디바이스 TFLite Zero-copy 연동 리스크

* **잠재 리스크**:
  * 네이티브 단의 프레임 프로세서 플러그인(worklets) 구현 난이도가 높고, 스마트폰 제조사별 AP와 드라이버 파편화로 인해 GPU/NPU 가속 가동 시 특정 기기에서 메모리 누수 및 오작동이 유발될 수 있습니다.
* **대처 방안**:
  * **안전한 CPU Delegate Fallback 적용**: 모바일 하드웨어 가속(Delegate) 빌드 시 예외 가드레일을 씌워 기기 특성상 초기화 실패 시 즉시 **CPU 스레딩 기반 TFLite 연산**으로 자동 다운그레이드되도록 설계합니다.

### [3] LLM 스로틀링 및 TTS 음성 캐싱 리스크

* **잠재 리스크**:
  * 변화 판단 임계치에 따른 스로틀링으로 인해 뒤늦게 다가오는 고위험 장애물의 가이드가 발송 누락될 우려가 있으며, 무제한 TTS 캐싱 적용 시 기기 내 가용 메모리(RAM)를 고갈시킬 수 있습니다.
* **대처 방안**:
  * **긴급 상황 무조건 우회(Reflex Override) 정책**: 스로틀링 게이트 상단에 우선순위 검증을 두어, 돌발 위협 상황이 감지되면 즉시 스로틀링 대기 타이머를 강제 파괴(Bypass)하고 비상 경보 및 가이드를 즉각 송출합니다.
  * **LRU 캐시 제한 설정**: 메모리 누수를 원천 차단하기 위해 오디오 캐시 용량 한도(예: 최대 100개 슬롯)를 하드코딩하고, 초과 시 가장 오랫동안 호출되지 않은 클립부터 삭제하는 **LRU(Least Recently Used) 알고리즘**을 결합합니다.

### [4] ngrok 고정 도메인 및 동적 설정 UI 리스크

* **잠재 리스크**:
  * ngrok 계정당 1개 제공되는 고정 도메인 제약으로 인해 다수 개발자가 동시 가동 시 충돌이 일어날 수 있으며, 시각장애인 단말의 설정 UI 노출로 인한 사용자의 오입력 고장이 초래될 수 있습니다.
* **대처 방안**:
  * **개발자 히든 제스처(Hidden Gesture) 모드 구축**: 일반 사용자가 연결 주소를 잘못 건드리는 사고를 예방하기 위해, 메인 화면의 여백을 5회 연속 터치하거나 길게 누르는 특정 제스처 수행 시에만 주소 입력 설정창이 노출되는 개발자 모드를 구현하고 **기본 주소 리셋 버튼**을 배치합니다.
