## 1. 핵심 결론

현재 골격은 좋습니다. 특히 **반사 경로와 인지 경로의 물리 분리**, **오프라인 온디바이스 반사**, **ANE 19~35ms 추론**, **선점/덕킹 오디오 설계**는 안전 보조 제품의 기본 방향과 잘 맞습니다.

다만 현재 상태는 **데모가 되는 것**과 **시각장애인이 실제로 의지할 수 있는 것** 사이에 아직 간극이 있습니다. 가장 큰 문제는 탐지 모델 자체보다 그 위층의 **안전 판단 공백**, **보행 중 음성 상호작용 지연**, **연결 신뢰성**, **안내 품질 검증 부재**, **당사자 관점 제품화 부족**입니다.

## 2. 안전에 직결되는 기능 공백

가장 치명적인 공백입니다. 장애물 탐지 데모가 되더라도, 도로 횡단, 보도 이탈, 방향 기준, 거리 판단이 불안정하면 실제 보행 보조로 신뢰하기 어렵습니다.

| 공백 | 현재 근거 | 왜 치명적인가 | 보완 방향 |
| --- | --- | --- | --- |
| **신호등 등화 상태 인식 없음** | Detection 29클래스에 `traffic_light`, `traffic_light_controller`는 있으나 적색/녹색 등화 상태 분류가 없습니다. 나아가 `traffic_light`는 정보성 클래스로 분류되어 인지 경로 채택 목록(`detection_pipeline.py`의 `MID_RISK_CLASSES`)에서도 제외되어 있어, **탐지되더라도 현재 어떤 안내에도 쓰이지 않습니다**. | 시각장애 보행에서 가장 위험한 순간이 도로 횡단인데, 현재는 "신호등이 있다"까지도 안내하지 못하고 "건너도 되는지"는 더더욱 알려주지 못합니다. | 신호등 상태 분류 데이터셋과 별도 상태 분류 헤드를 중기 로드맵으로 시작해야 합니다. |
| **횡단보도 클래스 부재** | Segmentation 4클래스는 `sidewalk_normal`, `caution`, `roadway`, `braille_normal`로 확정되어 있습니다. 최초 계획의 `crosswalk` 독립 클래스는 파인튜닝 확정 시 제외되었습니다(`surface_gate.py` 2026-07-07 정정 주석). | 횡단 지점 탐색과 정렬 안내가 원천적으로 어렵습니다. | `crosswalk`를 독립 노면 클래스로 추가하고, 보행 방향 정렬 안내와 연결해야 합니다. |
| **보도 이탈 감지 (거의 해소, 실기기 검증만 잔여)** | **2026-07-13 구현 완료**: 서버는 point-in-polygon 판정(`surface_departure.py`) + `DetectionConsumer._departure_streak` 기반 N프레임(3회) 히스테리시스로 확정한 뒤, `l1_classifier_node`가 `low`→`mid` 격상, `l2_generator_node`가 `braille_follow_direction()`(점자블록 폴리곤을 기준점 높이에서 가로지르는 x교차 구간 중점) 결과로 "왼쪽/오른쪽으로" 방향까지 포함한 LLM 프롬프트를 조립합니다. 온디바이스(`CoreMLInferenceBridge.swift`)도 `[1,32,160,160]` 프로토타입 마스크 텐서를 실제로 활용해(기준점 1픽셀만 `sigmoid(계수·프로토타입)` 내적으로 복원) `surfaceDeparture` 값을 계산하지만, 반사(햅틱/비프) 경로에는 의도적으로 연결하지 않고 로그로만 노출합니다(새 반사 트리거 오탐 위험 + 실기기 미검증). | "보도-차도 경계에서 벗어나고 있다", "점자블록을 따라가라"는 보행훈련 관점의 핵심 가치가 서버·온디바이스 양쪽에 코드로는 완성됐습니다. 남은 것은 실측뿐입니다. | **잔여(유일)**: 실기기 실측 - 서버 히스테리시스 임계값(3프레임)이 실사용에 적절한지, 온디바이스 단일 기준점이 세그멘테이션 경계 근처에서 얼마나 자주 뒤집히는지(노이즈). 확인용 로그(`[Pipeline] 보도 이탈 판정`, `[SurfaceDeparture][OnDevice]`) 준비 완료. |
| **거리 추정이 bbox 면적 휴리스틱 (부분 해소, 실측 잔여)** | 클라이언트는 `DetectionResult.distanceMeters`/`distanceSource` 계약을 열고, `CameraView.tsx` 표시와 반사 게이트가 LiDAR 값을 우선 사용하도록 변경했습니다. LiDAR 값이 없으면 기존 `0.22/sqrt(areaRatio)` 의사 거리와 면적 기반 반사 게이트로 fallback합니다. `DepthProbeBridge.swift`에는 bbox 중앙 50% 7x7 grid + 25퍼센타일 샘플링 helper(`probeBoxes`)가 추가됐습니다. `거리측정` 계측용 버튼은 같은 `AVCaptureSession` 안에서 video+depth를 `AVCaptureDataOutputSynchronizer`로 동기화하며, 동기화된 `cameraCalibrationData`가 있을 때만 프레임을 갱신합니다. depth 샘플 좌표는 `lensDistortionLookupTable`로 보정하고 `intrinsicMatrix` 기반 광선 스케일을 적용하며, 화면에는 보정 거리와 원본 z축 depth를 함께 표시합니다. | 테스트 기기인 iPhone 14 Pro Max는 LiDAR를 탑재하므로 ARKit depth 기반 실거리 경보가 가능합니다. "전방 3m 볼라드"와 "볼라드가 크게 보임"은 신뢰도가 다릅니다. | **잔여**: 계측용 "거리측정" 버튼의 0.3m·0.5m·1.0m·2.0m 줄자 실측과 방향별 보정 검증이 필요합니다. 정식 객체별 실거리 경보로 승격하려면 VisionCamera 탐지 프레임과 depth map이 같은 세션·같은 타임스탬프·같은 640x640 crop 좌표계임을 실기기에서 검증해야 합니다. |
| **방향 지시의 사용자 기준 좌표 미정의** | "우측으로 피하세요"가 카메라 프레임 기준입니다. | 단말 착용 방식이 정의되지 않으면 사용자 몸 기준 방향과 어긋날 수 있습니다. 흰지팡이와 폰을 동시에 들기 어렵기 때문에 착용 하드웨어 확정이 선행 조건입니다. | 체스트 마운트, 목걸이, 핸드헬드 중 기준 자세를 정하고, 카메라 좌표를 사용자 몸 좌표로 변환하는 규칙을 정의해야 합니다. |

## 3. 음성 상호작용의 보행 중 사용성 문제

이번 세션 실측 결과 기준으로, 현재 음성 상호작용은 보행 중 연속 사용을 버티기 어렵습니다.

| 문제 | 확인 근거 | 위험성 | 보완 방향 |
| --- | --- | --- | --- |
| **왕복 지연이 큼 (부분 해소 진행 중)** | `stt_audio` 수신 22:36:33, 처리 완료 22:36:41로 발화 1회에 약 5~8초가 걸렸습니다(당시 Whisper medium CPU, LLM, TTS 합산). **2026-07-11 `4ff207b`에서 기본 모델 `faster-whisper-small` 전환, 서버 기동 시 프리로드(콜드스타트 8~10초 제거), TTS 합성 캐시(고정 안내문 재합성 1.4~1.9초 제거)가 적용되었습니다.** small 인식 품질은 실기기 검증 대기 상태입니다. | "길댕아" → "길찾아줘" → 목적지 발화의 3턴 대화는 길에서 20~30초 이상 정지해야 할 수 있습니다. "길댕아 길찾아줘" 1턴 결합 발화는 인텐트 우선순위 수정으로 이미 처리되지만, 목적지까지 포함한 완전 원샷은 미지원입니다. | GPU 서버 실측 재검증, 목적지 포함 원샷 발화 파싱, 응답 스트리밍을 도입해야 합니다. 예: "길댕아 강남역 가는 길 알려줘"를 한 번에 처리합니다. |
| **실패 문구와 보행 명령 분리 완료** | `3e7ab52`에서 STT 빈 결과 안내를 "음성이 인식되지 않았어요. 다시 말씀해 주세요."로 교체했습니다. `source=stt-bridge-empty` 분기는 유지합니다. | 음성 인식 실패를 보행 정지 명령으로 잘못 연결하던 위험을 제거했습니다. | 해당 문구가 다시 위험한 행동 지시로 바뀌지 않도록 회귀 테스트를 유지해야 합니다. |
| **반사 비프가 STT를 오염함 (구현 완료, 검증 대기)** | 녹음 중에도 반사 경보가 계속 울리고, 파형 분석상 스피커 소리가 마이크에 되잡히는 것이 확인되었습니다. | **2026-07-11 구현**: STT 녹음 구간에서 iOS 세션을 `voiceChat` 모드로 전환해 AEC(VoiceProcessingIO)를 활성화하는 네이티브 브릿지(`AudioSessionBridge.swift`)를 추가했습니다. AEC 활성이 세션 조회로 확인된 경우에 한해 제거했던 녹음 시작 신호음도 복원했습니다(`STT_START_CUE_WITH_AEC` 플래그로 롤백 가능). | 실기기 청취 검증이 남았습니다: (1) 녹음 중 반사 비프가 전사에 섞이지 않는지, (2) 시작 신호음이 자기 녹음되지 않는지(기존 캡처 절단 가드가 회귀 감지), (3) `voiceChat` 전환 후 스피커 라우팅(`.defaultToSpeaker`)과 재생 음량이 실용적인지. Android AEC(AcousticEchoCanceler)는 후속 과제입니다. |
| **패닝 비프가 이어폰 전제** | 방향 경보가 좌우 게인을 구운 스테레오 WAV 5종입니다. | 시각장애인은 귀를 막는 이어폰이 위험하므로 골전도, 오픈이어, 스피커를 쓰는 경우가 많습니다. 스피커에서는 패닝 방향 정보가 약해집니다. | 방향 음성화, 예: "왼쪽 앞", 또는 햅틱 방향 패턴을 병행하고 골전도 헤드셋 실착 테스트를 해야 합니다. |
| **웨이크워드 인식률 미검증** | hotwords 배선은 있으나 실측 검증 전입니다. "길댕아"는 사전에 없는 신조어입니다. | 보행 중 호출 실패가 잦으면 음성 UX 전체가 무너집니다. | 전용 KWS 분리 또는 소량 파인튜닝이 필요합니다. |

## 4. 신뢰성 문제

이 도메인에서는 **가끔 되는 것**은 사실상 실패에 가깝습니다. 장애 상황을 사용자에게 알려주고, 가능한 기능 범위로 즉시 축소 운전해야 합니다.

| 문제 | 현재 상태 | 영향 | 보완 방향 |
| --- | --- | --- | --- |
| **네트워크가 데모 인프라** | ngrok 무료 터널, `config/index.ts` 하드코딩 LAN IP/도메인/정적 토큰(`token-abc-001`) 기반입니다. | 실사용 환경에서는 인증, TLS, 고정 도메인, 기기 식별이 부족합니다. | 고정 도메인, TLS, 기기 인증, 정적 토큰 제거가 필요합니다. |
| **끊김 처리 부족 (해소됨)** | **2026-07-11 해소**: 재연결을 포기하지 않고 지수 백오프(1s에서 2배씩, 최대 30s)로 무한 반복하며, 연속 3회 실패 시 폴백 모드 전환을 음성으로 고지하고("서버 연결이 끊겨 기본 경보 모드로 전환합니다. 연결은 계속 시도합니다.") 복구 시에도 음성 고지합니다("서버 연결이 복구되었습니다. 상세 안내를 다시 시작합니다."). 폴백 상태는 재시도 중에도 유지되어 온디바이스 경보 표시가 깜빡이지 않고, 재연결 카운터는 핸드셰이크 성공(welcome) 시점에 리셋되어 인증 실패 반복 시에도 백오프가 동작합니다(`useWebSocket.ts`, `config/index.ts`). | (해소 전) 사용자는 서버가 죽었는지, 기본 경보만 가능한지 알 수 없었습니다. | 실기기에서 서버 중단-고지-복구 고지 시나리오 검증이 남아 있습니다. |
| **서버 원인불명 재시작 미규명** | changelog 기준 FastAPI 컨테이너가 `exit 0`으로 3회 이상 스스로 재시작한 원인이 미확정입니다. | 운영 중 조용한 재시작은 안내 누락과 세션 단절로 이어질 수 있습니다. | 재시작 원인 규명, 헬스체크, 알림 체계, 컨테이너 종료 로그 보존이 필요합니다. |
| **장시간 프로파일 부재** | 30~60분 연속 보행의 발열, 배터리, 스로틀링 측정이 없습니다. | 짧은 데모에서는 되지만 실제 보행 시간에는 성능이 떨어질 수 있습니다. | ANE 전환 후 CPU 부하가 줄어든 상태에서 장시간 실측을 진행해야 합니다. 화면 상시 켜짐, 카메라 노출, 주머니 보관 불가 문제도 착용 방식과 함께 풀어야 합니다. |

## 5. 안내 품질 검증 체계 부재

안내문은 "그럴듯한 문장"이 아니라 실제 행동 지시입니다. 회귀 평가와 폐기 기준이 없으면 LLM 출력이 안전성을 흔들 수 있습니다.

| 검증 공백 | 현재 문제 | 필요한 체계 |
| --- | --- | --- |
| **LLM 안내문 안전성 평가 부재** | 로그에 "직진하며 차량을 지나가세요" 같은 문장이 확인되었습니다. 상황에 따라 위험한 지시일 수 있습니다. | 위험 상황 골든셋을 만들고, 차량 접근 중 직진 지시 금지 같은 규칙으로 L2 출력과 L3 가드레일을 회귀 평가해야 합니다. |

## 9. 최종 판단

Minchodan의 현재 구조는 데모용 장난감보다 훨씬 좋은 방향을 갖고 있습니다. 특히 반사 경로를 LLM/RAG/TTS에서 분리한 판단은 안전 도메인에서 매우 중요합니다.

그러나 실제 보행 보조 제품으로 가려면 다음 세 가지가 반드시 보강되어야 합니다.

| 필수 보강 축 | 핵심 질문 |
| --- | --- |
| **안전 판단** | 사용자가 도로, 보도 경계, 횡단보도, 신호등 앞에서 실제로 더 안전해지는가? |
| **실시간성** | 안내가 들리는 시점의 장면이 아직 유효한가? |
| **신뢰성** | 서버, 네트워크, STT, 오디오가 실패했을 때 사용자가 상황을 알 수 있는가? |

따라서 다음 단계는 기능을 많이 추가하는 것이 아니라, **제거된 위험한 오안내의 회귀를 막고**, **사용자에게 시스템 상태를 알려주며**, **당사자/O&M 검증으로 우선순위를 다시 세우는 것**입니다.
